# TradeFlow — API Specification

**Status:** FINAL / Canonical — synchronized with Baseline Hardened (migrations 001 + 002) and ADR-056 … ADR-063
**API Style:** REST/JSON over HTTP
**Backend:** Python + FastAPI
**Database:** PostgreSQL
**Client:** Flet

## 1. Purpose

This document defines the canonical application API boundary for TradeFlow. The API is the only application boundary between the Flet client and PostgreSQL.

```text
Flet Client
    ↓ HTTPS / HTTP REST
FastAPI
    ↓
Application Services
    ↓
Repositories
    ↓
PostgreSQL
```

The client must never connect directly to PostgreSQL.

## 2. Design Principles

1. Organization/tenant isolation is enforced by the backend.
2. Authorization is enforced by the backend, not only by UI visibility.
3. Business rules live in service/domain layers.
4. Financial values use decimal-safe representations.
5. Registered historical records are not physically deleted.
6. API responses use stable identifiers.
7. Validation errors are structured and machine-readable.
8. Audit is generated by the backend for sensitive operations.
9. The API remains industry-independent.
10. Messenger channels are external communication channels, not the API contract.

## 3. Versioning

Base path:

```text
/api/v1
```

Breaking contract changes require a new API version or an explicit compatibility strategy.

## 4. Authentication

### POST `/api/v1/auth/login`

Authenticates a user inside one organization (ADR-059). `username` is unique only within an organization, so the organization is part of the login.

Request:

```json
{
  "organization_code": "ORG-001",
  "username": "user1",
  "password": "********"
}
```

`organization_code` maps to `organizations.code`, which is added by migration 003 (`003_org_code_and_username.sql`, implemented and tested 2026-10-10).

Response:

```json
{
  "access_token": "<token>",
  "refresh_token": "<refresh-token>",
  "token_type": "bearer",
  "expires_in": 3600,
  "user": {
    "id": "uuid",
    "username": "user1",
    "organization_id": "uuid"
  }
}
```

The access token carries `organization_id` as the request context. Refresh tokens are bound to the same organization context. A user belongs to exactly one organization in the MVP.

Failure must not reveal whether the organization code, the username or the password was wrong (one generic 401).

### POST `/api/v1/auth/refresh`

Refreshes an access token using a valid refresh token.

### POST `/api/v1/auth/logout`

Invalidates the current session/refresh token according to the security implementation.

### GET `/api/v1/auth/me`

Returns the authenticated user and accessible organization context.

## 5. Organization Context

### GET `/api/v1/organizations`

Returns the organizations available to the authenticated user. In the MVP a user belongs to exactly one organization (ADR-059), so the list contains that single organization.

### GET `/api/v1/organizations/{organization_id}`

Returns organization details after authorization.

The API must reject access to organizations outside the user's authorized scope.

## 6. Customers

### GET `/api/v1/customers`

List customers within the current organization.

Supported query parameters may include:

```text
search
is_active
page
page_size
```

### POST `/api/v1/customers`

Creates a customer.

Example:

```json
{
  "customer_type": "COMPANY",
  "name": "Customer A",
  "national_id": "10101234567",
  "economic_code": "411112222333",
  "mobile": "09120000000",
  "phone": "02100000000",
  "address": "..."
}
```

Rules (ADR-061, C2/C3):

- `customer_type` is required: `INDIVIDUAL` or `COMPANY`.
- `name` is **not unique**. Only `national_id` and `economic_code` identify a customer inside an organization; a duplicate returns `409`.
- `national_id` and `economic_code` are normalized by the database: Persian/Arabic-Indic digits become ASCII digits, whitespace/ZWNJ/NBSP are removed, an empty string becomes `null`. The API returns the normalized value; the client must not rely on the raw input being stored.
- `organization_id` is never accepted from the body.

### GET `/api/v1/customers/{customer_id}`

Returns one customer after organization authorization.

### PATCH `/api/v1/customers/{customer_id}`

Updates editable customer information.

### DELETE `/api/v1/customers/{customer_id}`

Logical/deactivation behavior only where supported by the data model. Physical deletion of registered transactional history is prohibited.

## 8. Purchase Requests

### GET `/api/v1/purchase-requests`

Lists purchase requests for the current organization.

Query parameters:

```text
status
customer_id
created_from
created_to
search
page
page_size
```

### POST `/api/v1/purchase-requests`

Creates a purchase request. It is created in status `DRAFT`.

Example:

```json
{
  "customer_id": "uuid",
  "requested_delivery_date": "2026-11-15",
  "notes": "...",
  "items": [
    {
      "product_id": "uuid",
      "unit_id": "uuid",
      "quantity": "10.000",
      "unit_price": "125000",
      "discount_amount": "0",
      "tax_amount": "0",
      "specifications": []
    }
  ]
}
```

Rules:

- Money values are whole Rial integers sent as strings (`"125000"`, never `"125000.00"`); see § 17 and ADR-058.
- `request_number` is generated by the server (per-organization, per-series counter, ADR-057). It is never accepted from the client.
- `requested_delivery_date` is a calendar date `YYYY-MM-DD` (Asia/Tehran business day), optional, and must not be earlier than the request day; the same day is allowed.
- `quantity` has up to 3 decimals; `estimated_weight` is in KG with up to 3 decimals.
- `specifications` is stored per item as an **array snapshot** of `{field_id, field_code, field_name, data_type, value}` (ADR-061, C6). The array is built by the service when the item is saved; later changes to product specification master data never change it. The exact client-side request shape for specifications is fixed in the first-slice contract. The service validates each `value` against the field `data_type` (the database does not).
- Header totals (`subtotal`, `discount_total`, `tax_total`, `grand_total`) are computed by the server from the items; client-supplied totals are ignored/rejected.
- The backend validates that customer, products and units belong to the same organization, are active, and are permitted for use.

### GET `/api/v1/purchase-requests/{purchase_request_id}`

Returns the purchase request with items and relevant audit information permitted to the user.

### PATCH `/api/v1/purchase-requests/{purchase_request_id}`

Updates a request in status `DRAFT` only. Once the request is `SUBMITTED` or `CANCELLED`, its commercial content (customer, dates, totals, items) is frozen by the database (ADR-061, C5) and the API returns `409`. `request_number`, `organization_id`, `created_by` and `created_at` are immutable in every state.

### POST `/api/v1/purchase-requests/{purchase_request_id}/submit`

Submits a draft: `DRAFT → SUBMITTED`. Any other starting state returns `409`.

Allowed status transitions (enforced by the database, ADR-061 C5): `DRAFT → SUBMITTED`, `DRAFT → CANCELLED`, `SUBMITTED → CANCELLED`. `CANCELLED` is final.

### POST `/api/v1/purchase-requests/{purchase_request_id}/cancel`

Cancels a request only where the current state and permissions permit cancellation (`DRAFT` or `SUBMITTED` → `CANCELLED`).

> Part of the MVP endpoint set since ADR-062. Details (required `reason`, authorization, audit) are in `SLICE_01_CONTRACT.md`.

Physical deletion of a purchase request is not exposed by the API; the database permits deleting only a `DRAFT`.

## 9. Purchase Request Items

### POST `/api/v1/purchase-requests/{purchase_request_id}/items`

Adds an item to a purchase request in status `DRAFT`. If the parent is not `DRAFT`, the request fails with `409` (the database freezes items outside `DRAFT`). An item cannot be moved to another request.

### PATCH `/api/v1/purchase-request-items/{item_id}`

Updates an editable item.

### DELETE `/api/v1/purchase-request-items/{item_id}`

Removes an item only while the parent request is `DRAFT`. This is not a physical deletion of historical registered transactions: items of `SUBMITTED`/`CANCELLED` requests can never be removed.

## 10. Pricing

### POST `/api/v1/purchase-requests/{purchase_request_id}/pricing`

Registers or updates permitted pricing information.

The backend calculates/validates totals using decimal-safe arithmetic.

Canonical line calculation (ADR-058):

```text
line_total = ROUND_HALF_UP( quantity × unit_price − discount_amount + tax_amount )
```

- The result is a whole-Rial integer. The database enforces exact equality with `ROUND(…, 0)`; the application must use `decimal.Decimal` with an explicit context and `ROUND_HALF_UP` (Python's default `ROUND_HALF_EVEN` is forbidden; it disagrees with PostgreSQL on exact `.5` products).
- `discount_amount ≤ quantity × unit_price`; all amounts are ≥ 0.
- Header totals are rebuilt by the database from the items (`subtotal = Σ ROUND(quantity × unit_price, 0)`, `discount_total`, `tax_total` = sums, `grand_total = Σ line_total`).
- Pricing can be changed only while the request is `DRAFT`.

### GET `/api/v1/purchase-requests/{purchase_request_id}/pricing`

Returns current pricing and applicable history permitted by the user.

Material price changes must be auditable.

## 11. Audit

### GET `/api/v1/audit-logs`

Returns audit records subject to organization and permission restrictions.

Supported filters may include:

```text
entity_type
entity_id
actor_id
action
created_from
created_to
page
page_size
```

Audit records are read-oriented historical evidence. The database makes `audit_logs` append-only: `UPDATE`, `DELETE` and `TRUNCATE` are rejected (ADR-061, C4). The API exposes no write endpoint for audit; the backend creates audit records itself. Refresh tokens and passwords are never written to audit data.

## 12. Common Response Envelope

A successful collection response may use:

```json
{
  "items": [],
  "page": 1,
  "page_size": 50,
  "total": 0
}
```

A successful command response may use:

```json
{
  "data": {},
  "request_id": "uuid"
}
```

The exact envelope may be implemented consistently across all endpoints. The important requirement is contract consistency.

## 13. Error Contract

Errors must be structured.

Example:

```json
{
  "error": {
    "code": "PRODUCT_NOT_FOUND",
    "message": "Product was not found.",
    "details": {},
    "request_id": "uuid"
  }
}
```

Recommended HTTP mapping:

| HTTP | Meaning |
|---:|---|
| 400 | Malformed/invalid request |
| 401 | Authentication required/invalid |
| 403 | Authenticated but not authorized |
| 404 | Resource not found within authorized scope |
| 409 | Business/state conflict (illegal status transition, frozen request, duplicate) |
| 422 | Validation error |
| 500 | Unexpected server error |
| 503 | Temporary dependency/service unavailable |

The API must avoid leaking whether another organization's resource exists.

Database errors are mapped by the service, never returned raw:

| PostgreSQL | Meaning | HTTP |
|---|---|---|
| `55000` | State machine / freeze / append-only violation | 409 |
| `23505` | Unique violation (customer identifiers, request number, duplicate specification field) | 409 |
| `23503` | Foreign key / cross-organization reference, unknown specification field | 422 (or 404 where existence must not leak) |
| `23514` | Check violation (amounts, `line_total`, delivery date, specification element shape) | 422 |

## 14. Idempotency

Idempotency is a Phase 2 hardening capability for externally retried commands. Where implemented, commands that can be safely retried should accept an idempotency key.

This is especially important for future payment, release and accounting integration operations.

## 15. Pagination and Search

List endpoints should support stable pagination and bounded page sizes.

Search must remain organization-scoped.

Sorting must be deterministic where pagination is used.

## 16. Date and Time

Timestamps (`request_date`, `created_at`, …) use ISO 8601, UTC-aware. Calendar dates stored as `DATE` (currently `requested_delivery_date`) use `YYYY-MM-DD` and mean the Asia/Tehran business day.

Persian/Shamsi formatting is a presentation concern of the client and does not replace canonical backend date/time values.

## 17. Numeric Precision

Money values must not use binary floating-point semantics.

MVP money (ADR-058): the unit is **Rial** and every monetary amount is a whole number. JSON carries it as an integer string:

```json
{
  "unit_price": "125000",
  "discount_amount": "2500"
}
```

A value with a fractional part (`"125000.50"`, `"125000.00"`) is rejected with `422`. Toman, if shown, is a presentation concern of the client and never changes stored values.

Quantity (`NUMERIC(18,3)`) and estimated weight (`NUMERIC(18,3)`, KG) are decimal strings with up to 3 decimals.

## 18. Organization Isolation

Every tenant-scoped request is evaluated against the authenticated user's organization context.

A request attempting to reference another organization's:

- Customer
- Product
- Unit
- Purchase Request
- Item
- Document
- Audit record

must fail authorization/validation.

Database constraints should provide defense in depth where practical.

## 19. Security

Required controls include:

- Password hashing
- Access-token validation
- Refresh-token management
- Permission checks
- Organization isolation
- Input validation
- File/document authorization
- Audit logging
- Secure error handling
- No direct database access from client

## 20. Business Rule Boundary

The API must not implement critical rules only as endpoint/UI conventions.

Examples:

```text
Payment completion ≠ Release authorization
Loading ≠ Release
Proforma ≠ Final Accounting Invoice
Estimated Weight ≠ Actual Weight
```

These rules belong to application/domain services and are enforced regardless of client.

### Pre-Invoice (Stage 4, ADR-060) — written, not yet executed by its author

Binding contract: `SLICE_01_CONTRACT.md` § 26 (it wins on conflict). Same envelope, authentication, tenant isolation and error format as Slice 1; `organization_id` is never accepted from the client.

```text
POST /api/v1/purchase-requests/{id}/pre-invoices   body {} | {"supersedes_id": uuid}   → 201 DRAFT
GET  /api/v1/pre-invoices                          filters: status, source_request_id, customer_id, created_from, created_to, search, page, page_size
GET  /api/v1/pre-invoices/{id}                     detail + items + pdf metadata (never bytes)
POST /api/v1/pre-invoices/{id}/issue               → 200 ISSUED (number, version, pdf pending)
POST /api/v1/pre-invoices/{id}/cancel              body {"reason"?}  (DRAFT: optional; ISSUED: required)
POST /api/v1/pre-invoices/{id}/pdf                 generate / retry → 200 metadata | 500 PDF_GENERATION_FAILED | 429 RATE_LIMITED
GET  /api/v1/pre-invoices/{id}/pdf                 application/pdf (ETag = SHA-256) | 409 STATE_CONFLICT (PDF_NOT_READY)
```

Rules: statuses `DRAFT → ISSUED | CANCELLED`, `ISSUED → SUPERSEDED | CANCELLED`; illegal transition → `409 STATE_CONFLICT`; a second active document for a request/chain → `409 DUPLICATE_RESOURCE` (`details.reason`). SALES only reaches pre-invoices of requests it created (`403 FORBIDDEN_NOT_OWNER`); ACCOUNTING issues, cancels ISSUED and generates PDFs. `POST /purchase-requests/{id}/cancel` → `409 STATE_CONFLICT` (`ACTIVE_PRE_INVOICE`) while an ISSUED pre-invoice exists. A PDF failure never changes the commercial status; PDF limits: 10 MiB, ≥ 60 s between retries, ≤ 3 retries per fixed 15 minutes (the initial attempt is not a retry).

**Not implemented / future:** edit of a DRAFT, in-place revision, approval, validity period, prepayment, payment terms, per-company configuration. **Blocker:** no approved PDF library/font — the default renderer fails with `PDF_RENDERER_UNAVAILABLE`.

These endpoints remain subject to the complete workflow and authorization rules before implementation.

## 22. Accounting Integration API Boundary

TradeFlow must expose an integration boundary rather than hard-code a single accounting vendor.

Conceptual operations:

```text
POST /api/v1/integrations/accounting/export
POST /api/v1/integrations/accounting/sync
GET  /api/v1/integrations/accounting/status/{transaction_id}
```

The implementation is Phase 2/Future.

A connector should translate TradeFlow's canonical transaction data into the target accounting system's required structure.

TradeFlow must not assume that an accounting system's invoice ID, journal ID or document model is identical to its own.

## 25.1 Implementation Notes for the MVP Set

- Every query is scoped by the `organization_id` from the token; no endpoint takes it from a body or query.
- `organization_code` login requires migration 003 (implemented; the login endpoint itself is not implemented yet).
- Services must validate: active customer/product/unit, specification `value` against `data_type`, required specification fields, and permissions. These are not enforced by the database.

## 26. Implementation Rule

An endpoint must not be implemented merely because it appears in this document. The implementation must first satisfy:

1. Data Model
2. Workflow rule
3. ADR decision
4. Authorization rule
5. Audit requirement
6. UI requirement, where applicable

This prevents API surface area from becoming a second undocumented business model.
